# Publishing JobPilot on Google Play (internal testing)

Decided with the owner on 2026-10-09: the app goes to Google Play's **internal testing** track only, for the owner
(up to 100 testers chosen by e-mail, no closed-test requirement, no store listing). Gmail stays a personal feature (the
Google Cloud project is not verified for restricted scopes). The owner already has a Play developer account.

Most steps are automated:

| What | How |
|---|---|
| Tools, signing key, GitHub secrets, fingerprints, first bundle, service account secret, new releases | `android/scripts/Play-Wizard.ps1` (Windows, interactive; Spanish) |
| Signed Android App Bundle (`.aab`), tests, upload to Play | `.github/workflows/android-release.yml` |
| Upload through the Play Developer API | `android/scripts/play_upload.py` (standard library + `openssl`) |
| Creating the app, the first upload, tester list, OAuth client, service account permissions | Play Console / Google Cloud console (manual; the wizard opens each page and says what to click) |

Run the wizard from the repository folder in PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File android\scripts\Play-Wizard.ps1
```

It shows a checklist, starts at the first step not done, and keeps its progress (no secrets) in
`%LOCALAPPDATA%\JobPilot\play-wizard.json`. The steps below are the same as the wizard's.

## 1. Tools

- GitHub CLI (`winget install --id GitHub.cli`), signed in with `gh auth login` to an account with access to the
  repository.
- A JDK for `keytool` (`winget install --id Microsoft.OpenJDK.21`); Android Studio's `jbr` also works.

## 2. Signing key (upload key)

The same keystore that signs the APKs in CI is Play's **upload key**. The four secrets `ANDROID_KEYSTORE_BASE64`,
`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD` already exist in the repository (CI produced
signed APKs). The wizard only needs the keystore file to read its fingerprints; it can also create a new key (outside the
repository, in `%USERPROFILE%\JobPilot-firma`) and load the secrets, with GitHub CLI asking for the passwords directly.

With Play App Signing (the default for new apps), Google keeps the key that signs the app users install; the upload key
only proves that bundles come from you. If the upload key is lost, Google can reset it; the APKs built by CI, however,
can only be updated with the same key, so keep a private backup of the keystore and its password.

## 3. Fingerprints

`keytool -list -v -keystore <file> -alias jobpilot` prints the SHA-1 and SHA-256. The upload key's SHA-1 belongs to the
Android OAuth client of the CI-built APKs (phase A8). The app installed from Play is signed with Google's key, which
needs its own client (step 7).

## 4. First bundle

Run **Actions → Android release (Google Play) → Run workflow** with "Upload to Google Play" unchecked, or let the wizard
do it (`gh workflow run android-release.yml -f upload=false`). The workflow tests the app, builds the signed `.aab` and
keeps it as the artifact `JobPilot-play-<n>` for 30 days. The version code is the workflow's run number; the version name
is `0.1.<n>`, or `1.2.3` for a tag `v1.2.3`.

## 5. Play Console (once, by hand)

Google requires the first bundle of a new app to be uploaded in Play Console.

1. **Create app**: name JobPilot, default language Spanish (Latin America) `es-419`, App, Free, accept the declarations.
2. **Test and release → Internal testing → Testers**: create an e-mail list with the Google account of your phone, select
   it and save.
3. **Create new release**: keep the recommended Play App Signing option (key generated by Google), upload the `.aab`
   from step 4, then **Save and publish** (roll out). Internal tests can start before the app setup tasks are complete
   and are exempt from the Data safety section; if Play Console still asks for something, fill it in as it indicates.
4. Copy the testers' **join link** (Internal testing → Testers).
5. **App integrity → App signing**: copy the **app signing key** SHA-1 (not the upload key's) for step 7.

## 6. Service account (publish from GitHub)

1. In the Google Cloud project used for the app's Google sign-in, enable the **Google Play Android Developer API**.
2. **IAM & Admin → Service accounts → Create**: `jobpilot-play`, no roles. Then **Keys → Add key → JSON**.
3. Play Console → **Users and permissions → Invite new users**: the service account's e-mail, app permission for
   JobPilot with **Release apps to testing tracks**.
4. Load the JSON into the `PLAY_SERVICE_ACCOUNT_JSON` secret (the wizard validates it and offers to delete the local
   file). `android/scripts/check-no-signing-keys.sh` fails CI if a service account key is ever committed.

## 7. Google sign-in for the Play build

Google Cloud → **Google Auth Platform → Clients → Create client → Android**, package `com.vidi.jobpilot`, SHA-1 of
Play's **app signing key** (step 5.5). Keep the existing Android client for the CI APKs: each signing key needs its own
client. The app embeds no client id, so nothing changes in the code. Under **Audience**, keep your account as a test user
(Testing) or publish the consent screen for personal use: unverified apps show an "unverified app" screen and are limited
to 100 users.

## 8. New releases

- Wizard step 8, or **Actions → Android release → Run workflow** (upload checked, track internal), or push a tag
  `v1.2.3`.
- The workflow uploads the bundle with `play_upload.py`: service account JWT → access token, then `edits.insert`,
  `edits.bundles.upload`, `edits.tracks.update` (status `completed`) and `edits.commit`.
- Choose status `draft` to review the release in Play Console before rolling it out.

## 9. Installing on the phone

The app from Play and the APK from GitHub are signed with different keys, so one cannot update the other. Before
switching: in the old app, **Configuración → Exportar / Importar → Exportar y compartir** (save the file somewhere you
can reach from the phone), uninstall it, open the join link with the tester account, install from Play, enter the Gemini
key again, reconnect Google and **Importar y combinar** the file.

## Store listing (optional for internal testing)

`android/docs/play/icon-512.png` is the 512×512 32-bit PNG icon for **Store presence → Main store listing → App icon**,
rendered from the launcher icon (`src/JobPilot.Mobile/Resources/AppIcon`, white briefcase on `#594AE2`). Play rounds the
corners itself. If the launcher icon changes, render this file again from the same SVGs.

`android/docs/play/feature-graphic-1024x500.png` is the **Feature graphic** (1024×500, 24-bit PNG without alpha): the icon
tile, the name and the tagline "Tu búsqueda de trabajo remoto, en el bolsillo." (es-419, the listing's default language) on
the icon's purple, next to a flat illustration of a man standing on a bus using his phone. Text and the illustration stay away
from the edges. `feature-graphic-1024x500-en.png` is the same image with the English tagline "Your remote job search, in
your pocket." for an English (en-US) translation of the listing.

## Other testers

Anyone added to the testers list (up to 100) can install the same app. Each person enters their own Gemini key (charged to
their account; the paid tier keeps Google from using the content to improve its products) and connects their own Google
account; the data stays on their phone and nothing reaches the owner. The app starts without seeds (empty profile, no keywords, no
followed companies) and the Panel lists the first steps. For Gmail and Calendar they use the owner's Google Cloud project: while the consent screen is
in Testing, add their e-mail as a test user under **Audience**; they see the "unverified app" screen (unverified apps are
limited to 100 users), and accounts in Advanced Protection cannot use Gmail.

## Troubleshooting

| Message | Cause and fix |
|---|---|
| `Only releases with status draft may be created on draft app` | The app has never been released: do step 5 by hand first. |
| `Package not found` / `The caller does not have permission` | The app does not exist yet, or the service account was not invited with access to it (step 6.3). Permissions can take a few minutes. |
| `APK specifies a version code that has already been used` | A re-run reuses the run number: start a new run instead of re-running. |
| Google sign-in fails with a developer error in the Play build | The Play app signing SHA-1 is missing from the Android OAuth clients (step 7). |
| The signing secrets error in the workflow | Step 2: the `ANDROID_*` secrets are missing. |

## Verified facts (2026-10-09)

- Personal developer accounts created after 13 Nov 2023 need a closed test with at least 12 testers opted in for 14
  consecutive days before production access (not needed for internal testing). Source:
  `https://support.google.com/googleplay/android-developer/answer/14151465`.
- Internal tests: up to 100 testers by e-mail list; may start before app setup is complete; may not be subject to the
  standard reviews; exempt from the Data safety section. Source:
  `https://support.google.com/googleplay/android-developer/answer/9845334`.
- From 31 Aug 2026 new apps and updates must target API 36 (the app does). Source:
  `https://developer.android.com/google/play/requirements/target-sdk`.
- Google Play requires Android App Bundles; the first bundle must be uploaded through Play Console. Source:
  `https://learn.microsoft.com/en-us/dotnet/maui/android/deployment/publish-google-play?view=net-maui-10.0`.
- New apps are enrolled in Play App Signing with a Google-generated key; the app signing key's fingerprints are under
  App integrity → App signing. Source: `https://support.google.com/googleplay/android-developer/answer/9842756`.
- Play Developer API: service account invited in Play Console; `edits.bundles.upload` at
  `/upload/androidpublisher/v3/applications/{package}/edits/{edit}/bundles`, scope `androidpublisher`; track releases
  with status `draft|inProgress|halted|completed`; `edits.commit` at `.../edits/{edit}:commit`. Sources:
  `https://developers.google.com/android-publisher/getting_started`,
  `https://developers.google.com/android-publisher/api-ref/rest/v3/edits.bundles/upload`,
  `https://developers.google.com/android-publisher/api-ref/rest/v3/edits.tracks`.
- Service account tokens over REST: RS256 JWT (`iss`, `scope`, `aud` = `https://oauth2.googleapis.com/token`, `iat`,
  `exp` ≤ 1 h) exchanged with `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`. Source:
  `https://developers.google.com/identity/protocols/oauth2/service-account`.
- `USE_EXACT_ALARM` is limited to alarm, timer and calendar apps and needs a Play Console declaration;
  `SCHEDULE_EXACT_ALARM` (what the app uses) is the user-granted alternative. Source:
  `https://support.google.com/googleplay/android-developer/answer/16558241`.
- Restricted scopes (Gmail) for public apps need verification and an annual security assessment. Source:
  `https://support.google.com/cloud/answer/13464321`.
- Android developer verification is in effect in Brazil, Indonesia, Singapore and Thailand since 30 Sep 2026, global
  roll-out from 2027; apps on Google Play come from verified Play developers. Source:
  `https://support.google.com/android-developer-console/answer/16561738`.
